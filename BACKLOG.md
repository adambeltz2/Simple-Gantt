- [x] ~~[BUG] PDF export renders wrong -- user-reported screenshot shows the exported page with content squeezed into a small box in the top-left corner and the rest of the page blank, instead of the full-page chart tiling described in backlog item #7.~~ -- **fixed in v2.15.4.** Root cause wasn't the tiling/scaling math (that part was already correct) -- it was `captureChartCanvas()` itself. Confirmed directly against the real html2canvas 1.4.1 source and reproduced/fixed in an isolated headless-browser harness (the previously-shipped width-only fix from v2.15.0 was verified to still fail this same way) before touching production code. Fixed by neutralizing the overflow on the cloned `.chart-panel` and `.gantt-container` via html2canvas's `onclone` callback, pinning them to their true full-content dimensions instead.
- [x] ~~[BUG] Grid-typed or Bulk-Edited Resource names weren't reaching the named-resources registry (backlog #12).~~ -- **fixed in v2.22.1.** The registry only picked up a new name via CSV import's merge step; typing a not-yet-registered name directly into a grid Resource cell, or setting one via Bulk Edit, assigned it to the task fine but never added it to the Resource Manager or that cell's own quick-pick popover. - [x] ~~[BUG] A resource assigned to a task with no Start/Duration silently vanished from the Workload dashboard.~~ -- **fixed in v2.23.1.** User-reported: a resource typed into the grid didn't show up on the Workload dashboard, which looked like a repeat of the named-resources registry bug above -- but the registry itself was fine (verified with a real Playwright run simulating an actual click-and-type in the grid). Fixed by having `renderWorkloadTable()` track resource names that are assigned only to such not-yet-scheduled tasks and surface them explicitly -- named directly in the empty state when nothing else has a schedule yet, or called out in a note below the table when other tasks do render.
- [x] ~~[BUG] "Move row up/down" never produced an Undo step, since Undo/Redo shipped in v2.23.0.~~ -- **fixed in v2.29.0.** `moveRow()` wrote its reordered data into `appDB.projects[...].data` *before* calling `syncToGantt()`, so by the time `saveToLocal()` ran its before/after diff to decide whether to push an Undo snapshot, both sides of that diff were already the same object -- every row-swap silently vanished from Undo history. Found while building backlog #21's own move function, which had the identical bug freshly introduced; fixed both by leaving that assignment to `saveToLocal()` itself, which already sets it at the correct point in the diff.
- [x] ~~[BUG] "Delete row" from the grid's right-click menu only deleted one row out of a dragged multi-row selection.~~ -- **fixed in v2.33.1.** (User-reported. - [x] ~~[BUG] A parent row nested under another parent (depth > 0) wasn't rendered bold, even though top-level parents were.~~ -- **fixed in v2.33.2.** (User-reported, with a screenshot circling the specific nested parent rows that stayed regular weight despite having their own children/collapse toggle. - [x] ~~[BUG] A parent showed 100% Done even though most of its children were blank/unscheduled.~~ -- **fixed in v2.33.3.** (User-reported, with a screenshot: "CPQ Templates" showed 100% with ~30 children, but only one had an actual schedule/progress -- the rest were entirely blank. Root cause in `syncToGantt()`'s parent rollup: the % Done weighted average ran over the same schedule-only child subset used for the date-span rollup, so an unscheduled child was invisible to the average instead of counting as 0% -- a lone scheduled child at 100% could make the whole parent read 100%. Fixed with `backfillResourcesRegistry()`, run once per project alongside `normalizeData()`/`migrateLegacyNotesColumn()` on every load, additive-only and idempotent.)
- [x] ~~[BUG] Landscape mobile was stuck in the same single-pane-only mode as portrait.~~ -- **fixed in v2.31.1.** User-reported: rotating a phone to landscape kept the workspace locked to one full-width pane, same as portrait, even though a landscape phone is often 700-860px wide -- real room for the desktop-style side-by-side split. - [ ] **[DEBT] `importDiscoveredProject()`'s CSV header parsing has no legacy-shape migration at all.** Found while adding the core Notes column (backlog #22): `applyImportedCSVData()` (used by manual Import and Dropbox "Restore") has always handled a CSV exported before Labels (and now Notes) existed by detecting the missing header and splicing in a blank column at the right position, so older exports still land every custom column correctly. `importDiscoveredProject()` -- the "Check Dropbox for other projects not in this browser" bulk-import path -- parses headers the same way (`headers.slice(N)`) but has never had that same legacy-shape check, so importing a very old cross-device backup (predating Labels, or now predating Notes) through *that* specific path would misalign its custom-column data by one or two slots instead of shifting it correctly. Worth a real fix (reusing `applyImportedCSVData`'s splicing logic, or better, having both paths share one header-normalization helper) next time this area is touched.

Grounded in how Dropbox integration actually works (`index.html`, ~line 1172 on): the task grid's `localStorage` copy is *already* the sole source of truth for every edit -- `saveToLocal()` runs synchronously on every grid change regardless of Dropbox -- and Dropbox backup (`backupToDropbox()`) is a one-way, best-effort, 60s-debounced *push* of a timestamped CSV snapshot (`mode: 'add'`, never overwriting a prior backup file), not a live two-way sync. (4) No merge/reconciliation UI was added -- a code comment on `handleDropboxAuthError()` documents why: nothing here ever mutates `localStorage` in response to a Dropbox failure, so the very next backup after reconnecting just pushes current state as a new snapshot exactly as it always did.
    - **Deliberately deferred, lower priority:** item 5, a proactive token-validity probe at reconnect/resume time (rather than only discovering a dead token reactively via whatever Dropbox call happens to fire next), so the "disconnected" status could appear as soon as the app loads instead of after the first failed background attempt. Two surprises in what came back: (1) the live `jsuites.js` is `jsuites@4.17.5` -- one patch behind npm's own current `4.x` tip (`4.17.7`), confirmed via the file's embedded `Version` string, so the CDN doesn't auto-track npm's latest; (2) the live `jexcel.js` is **not** the deprecated standalone `jexcel` npm package (frozen at `4.6.1`, and which literally logs a "renamed to Jspreadsheet" deprecation notice on load) -- it's the renamed successor package `jspreadsheet-ce@4.15.0`'s `dist/index.js`, byte-for-byte, just served under the legacy `jexcel.js` filename for backward compatibility. (`jspreadsheet-ce@4.15.0`'s own `package.json` claims a `jsuites ^5.6.5` dependency; that's stale/wrong metadata -- the pairing actually served live, and the one pinned here, is `jsuites@4.17.5` + `jspreadsheet-ce@4.15.0`, confirmed by direct byte comparison against real npm tarballs, not by trusting the declared semver range.) Now pinned via jsdelivr with real SRI hashes computed from the npm-published bytes. Re-verified the full Playwright suite against real vendored copies of this exact pairing before pinning -- zero new failures, only the same pre-existing unrelated baseline (PDF export libs not vendored in the throwaway harness, reload-persistence and PWA service-worker tests not surviving mocked CDN routing, one row-id-backfill timing quirk specific to the vendored build).
- ~~[DEBT] Review the Playwright suite (`tests/*.spec.js`, 30 files) for redundant tests and optimize the overall testing approach.~~ -- **done.** All 30 spec files independently duplicated the exact same `test.beforeEach` boilerplate (navigate to `/index.html`, wait for the grid, and wire a `page.on('pageerror', ...)` listener into `page.consoleErrors`), and most files then spent one whole dedicated test at the end just replaying an earlier scenario to assert that listener came back empty -- meaning a JS error thrown during any of a file's *other* tests went unchecked unless that exact action sequence happened to be the one replayed. Four files (`inclusive-end-dates`, `late-flag`, `sibling-indent-alignment`, `timezone-safety`) captured `page.consoleErrors` but never asserted it anywhere at all -- dead instrumentation. Fixed by extracting the shared setup into one Playwright fixture (`tests/fixtures.js`, `test.extend()`'s `page` fixture) that does the navigation once and automatically asserts zero uncaught errors after *every* test in every file, not just a hand-picked scenario -- strictly more error-checking coverage with far less duplicated code, and it retroactively fixes the four files that were silently not checking at all. With that in place, 19 dedicated "no console/JS errors" tests across `bulk-edit`, `clear-all-filters`, `collapse-expand`, `critical-path`, `dependency-cycle-detection`, `done-checkmark`, `dropbox-pagination`, `export-menu`, `flag-in-progress`, `grid-search`, `labels`, `leaf-end-date`, `move-task-to-id`, `named-resources`, `pdf-export`, `project-notes`, `resource-colors`, `row-id-backfill`, `structured-filters`, and `undo-redo` were true duplicates -- each one just replayed actions an earlier test in the same file already exercised, with no assertion of its own beyond the error check the new fixture now runs unconditionally -- and were removed outright. A further ~9 tests that tacked a redundant trailing `expect(page.consoleErrors).toEqual([])` onto an otherwise-real assertion (e.g. `dependency-scheduling`'s Sync Dependencies test, three in `workload-dashboard`) kept their real assertions with just that now-implicit line dropped. Net: suite goes from 30 files / 258 tests to 30 files / 239 tests, with equal-or-better error coverage (every remaining test is now checked, not just the ones that said so) and no loss of any unique behavioral assertion -- verified by running the full suite (`npx playwright test`) before and after.
