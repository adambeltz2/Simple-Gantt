## Bug
- [x] ~~Upon login its to check for projects that aren't successfully imported which could occur if you were working in another browser or on another device. This is not currently working.~~ -- **fixed in v2.15.3.** (Automatic discovery was only ever wired to the one-time OAuth callback (`isFreshDropboxLogin`), not to normal page loads where the Dropbox token already persists in `localStorage` -- which is every session after the first. Now runs on every load where a token is present; stays silent when nothing new is found.)
- [ ] **[BUG] Dropbox cross-device project discovery still not finding real projects (reopened -- v2.15.3's fix wasn't sufficient).** User-reported, reproduced in Firefox: clicking "Check Dropbox for other projects not in this browser" (`discoverDropboxProjects(true)`) reports "No additional Dropbox projects found," even though projects exist in Dropbox that aren't in that browser. The one concrete gap found on code review -- `dbx.filesListFolder()`'s four call sites never following up on `has_more`/`cursor`, silently dropping anything past the first page -- **is fixed**: all four now go through a shared `listAllDropboxEntries()` helper (`index.html`) that walks every page via `filesListFolderContinue()`, verified both in isolation and through `discoverDropboxProjects()` end-to-end against a fake paginated client where the missing project sits on page 2 (`tests/dropbox-pagination.spec.js`). Left open because this may not have been the user's actual cause -- it only bites once a Dropbox account has enough backed-up project folders to cross Dropbox's per-page limit, and the other live possibility (a different Dropbox account/session logged in per browser) is still unconfirmed either way. Needs the user to retest and report back before this can be closed.
- [x] ~~[UX] Labels column's multi-value delimiter (`;`) isn't discoverable, and conflicts with Resource's (`,`).~~ -- **fixed.** Rather than just documenting which delimiter to use, Resource and Labels now both accept either `,` or `;` interchangeably (even mixed in the same cell) via a new shared `splitMultiValueCell()` helper (`index.html`), so whichever habit a user reaches for works in both places. `Depends` deliberately keeps `;` only -- its cycle detection and existing tests assume that single delimiter, and a Task ID can't contain a comma to begin with, so there's no real ambiguity to unify there.
- [x] ~~[BUG] PDF export renders wrong -- user-reported screenshot shows the exported page with content squeezed into a small box in the top-left corner and the rest of the page blank, instead of the full-page chart tiling described in backlog item #7.~~ -- **fixed in v2.15.4.** Root cause wasn't the tiling/scaling math (that part was already correct) -- it was `captureChartCanvas()` itself. Both `.chart-panel` and frappe-gantt's nested `.gantt-container` have `overflow: auto` in their live CSS, and that CSS survives into html2canvas's cloned document: no matter how large a `width`/`height`/`windowWidth`/`windowHeight` you ask html2canvas for, the cloned elements still visually clip to their own on-screen scrolled box, so only whatever already fit in the visible viewport got captured -- exactly the "small box, rest blank" symptom. Confirmed directly against the real html2canvas 1.4.1 source and reproduced/fixed in an isolated headless-browser harness (the previously-shipped width-only fix from v2.15.0 was verified to still fail this same way) before touching production code. Fixed by neutralizing the overflow on the cloned `.chart-panel` and `.gantt-container` via html2canvas's `onclone` callback, pinning them to their true full-content dimensions instead.

1. ~~Grid search/filter~~ -- **done in v2.11.0.** (Turned out jexcel's own built-in `search()` wasn't safe to build on -- it manages row visibility by detaching `<tr>` elements from the DOM, which would have fought with Collapse's `hideRow`/`showRow` mechanism. Built as an extension of the existing `applyRowVisibility()` instead.)
2. ~~Resource color-coding~~ -- **done in v2.12.0.** (Deterministic alphabetical name-to-color mapping; a 4px stripe on the bar's left edge, layered on top of the status fill so it stays visible at any progress %; first-listed resource wins on multi-resource tasks; matching section added to the chart legend.)
3. ~~Explicit dependency cycle detection~~ -- **done in v2.13.0.** (Three-color DFS over the Depends graph, run once per sync; a detected cycle gets a red outline + tooltip on every Task ID involved plus a one-time status warning, never a mutation of the Depends column. Also fixed a real pre-existing bug found along the way: `syncToGantt`'s status warnings, including the existing self-reference one, were being silently overwritten by "✓ Saved" before ever reaching the screen.)
4. ~~Task duplication/templates~~ -- **declined.** Not wanted; left here only as a record that it was considered.
5. ~~Critical path highlighting~~ -- **done in v2.14.0.** (Opt-in toolbar toggle, off by default; a real CPM forward/backward pass over the Depends graph, expressed with the same working-day-aware date arithmetic the live scheduler already uses. ⚡ icon in the grid, outlined bar in the chart, legend entry. Suppressed while a dependency cycle exists.)
6. ~~Flag a task as "IN PROGRESS", highlighting the whole row~~ -- **done in v2.6.0**, predating this list's own tracking of it. (Shipped as a click toggle -- the ● marker next to any Task ID -- rather than the right-click-on-the-row mechanism originally proposed here; toggling tints the row purple and is grid-only, stored per project alongside collapse state, with zero footprint in the Gantt chart, CSV export, or Dropbox backups.)
7. ~~PDF export~~ -- **done in v2.15.0.** (jsPDF, pinned + SRI-hashed, tiling the same html2canvas rasterization the PNG export uses across as many landscape pages as a wide timeline needs. Also fixed a real pre-existing bug found along the way: PNG/PDF export only ever captured the currently-scrolled-into-view slice of the chart, not the full timeline, because the actual horizontal scroll lives on frappe-gantt's own nested `.gantt-container`, not `.chart-panel` itself.)
8. ~~Baseline / plan-vs-actual tracking~~ -- **declined.** Not wanted; left here only as a record that it was considered.
9. ~~Add Filter for any column~~ -- **done in v2.16.0.** (The existing grid search now matches every column's value, not just Task Name/Resource -- % Done included, per the specific ask here. Same matching/visibility semantics as before, just widened to check the whole row.)
10. ~~After a task is marked 100% complete the highlighting/conditional format for late based on due date should be removed~~ -- **fixed in v2.16.1.** (The Gantt chart bar already checked % Done before overdue -- `is-complete` took precedence over `is-overdue` in `syncToGantt`'s custom-class logic. The grid's End-date cell coloring didn't: `computeLateStatus()`, used by `formatCells` for the End column's red/yellow background, was pure date math against today that deliberately ignored % Done, so a task finished after its End date passed stayed marked overdue in the grid forever. `computeLateStatus()` now takes % Done and returns no status once a task hits 100%, matching the chart's own precedence.)

11. **Undo/redo** -- there's no in-app undo today (the README just points at the browser's Ctrl+Z, which isn't reliable for a JS grid). Highest risk: it's not just about reverting a raw cell edit -- every edit can cascade through dependency scheduling and parent rollup, so a naive undo could easily leave the sheet in an inconsistent state (a reverted Start/Dur with stale computed End/rollup values). Needs real design thought before any code, not just a wrapper around jexcel's own internal history.
12. Treat Resources as first class entity. I'd like them to be assigned (named) prior to being typed in the grid. This should allow a pre-selected value for me to use. Discuss how to handle this when its done via CSV Import/Export.
13. ~~Add Label functionality to a line~~ -- **done in v2.17.0, filter upgraded to multi-select in v2.18.0.** (New "Labels" grid column, right after Parent -- free-text, accepting `,` or `;` so a row can carry many labels, one, or none, rather than a separate managed/colored entity, per backlog #12's own note that formality is unresolved complexity there. The toolbar filter is a checkbox multi-select, not a single dropdown: checking one or more labels narrows the grid to tasks carrying ANY of them (OR, not AND) -- primary, as asked -- and an opt-in "Label in chart" toggle, off by default, applies that same filter to the Gantt chart as the requested secondary option, e.g. isolating "System A" and "System B" together while staying a toggle away from the full plan.)
14. ~~Bulk edit / multi-row select~~ -- **done in v2.19.0.** (A "Bulk Edit" toolbar button: click-and-drag to select 2+ rows, pick Resource/% Done/Parent, enter one value, apply to the whole selection. Selection is tracked via jexcel's `onselection` callback into an app-level variable rather than reading `selectedCell` at click time, since jexcel's own global mousedown handler clears that the moment a click lands on the toolbar button itself. A read-only row in the selection (e.g. a parent's computed % Done) is skipped via the grid's existing `isReadOnly()`, not a duplicated rule set, and called out separately in the confirmation message.)
15. **Mobile responsiveness and PWA support** -- the layout (split grid/chart panes, jexcel's own grid interactions, the toolbar) is built and tested for a desktop-width screen only; nothing today targets touch input or a narrow viewport. Highest risk/complexity item on the list: a real mobile-usable Gantt grid likely needs its own responsive layout strategy (e.g. a stacked or single-pane-at-a-time view below some breakpoint, touch-sized tap targets, jexcel's own touch-drag behavior verified), and PWA support on top of that (a web app manifest, an icon set, a service worker for offline caching) touches how the app is served/installed, not just its CSS. Needs real design/UX thought on what "mobile Gantt editing" should even look like before writing code, not just a `@media` pass over the existing desktop layout.
