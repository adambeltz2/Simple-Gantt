- [x] ~~Upon login its to check for projects that aren't successfully imported which could occur if you were working in another browser or on another device. This is not currently working.~~ -- **fixed in v2.15.3.** (Automatic discovery was only ever wired to the one-time OAuth callback (`isFreshDropboxLogin`), not to normal page loads where the Dropbox token already persists in `localStorage` -- which is every session after the first. Now runs on every load where a token is present; stays silent when nothing new is found.)
- [ ] **[BUG] Dropbox cross-device project discovery still not finding real projects (reopened -- v2.15.3's fix wasn't sufficient).** User-reported, reproduced in Firefox: clicking "Check Dropbox for other projects not in this browser" (`discoverDropboxProjects(true)`) reports "No additional Dropbox projects found," even though projects exist in Dropbox that aren't in that browser. The one concrete gap found on code review -- `dbx.filesListFolder()`'s four call sites never following up on `has_more`/`cursor`, silently dropping anything past the first page -- **is fixed**: all four now go through a shared `listAllDropboxEntries()` helper (`index.html`) that walks every page via `filesListFolderContinue()`, verified both in isolation and through `discoverDropboxProjects()` end-to-end against a fake paginated client where the missing project sits on page 2 (`tests/dropbox-pagination.spec.js`). Left open because this may not have been the user's actual cause -- it only bites once a Dropbox account has enough backed-up project folders to cross Dropbox's per-page limit, and the other live possibility (a different Dropbox account/session logged in per browser) is still unconfirmed either way. Needs the user to retest and report back before this can be closed.
- [x] ~~[UX] Labels column's multi-value delimiter (`;`) isn't discoverable, and conflicts with Resource's (`,`).~~ -- **fixed.** Rather than just documenting which delimiter to use, Resource and Labels now both accept either `,` or `;` interchangeably (even mixed in the same cell) via a new shared `splitMultiValueCell()` helper (`index.html`), so whichever habit a user reaches for works in both places. `Depends` deliberately keeps `;` only -- its cycle detection and existing tests assume that single delimiter, and a Task ID can't contain a comma to begin with, so there's no real ambiguity to unify there.
- [x] ~~[BUG] PDF export renders wrong -- user-reported screenshot shows the exported page with content squeezed into a small box in the top-left corner and the rest of the page blank, instead of the full-page chart tiling described in backlog item #7.~~ -- **fixed in v2.15.4.** Root cause wasn't the tiling/scaling math (that part was already correct) -- it was `captureChartCanvas()` itself. Both `.chart-panel` and frappe-gantt's nested `.gantt-container` have `overflow: auto` in their live CSS, and that CSS survives into html2canvas's cloned document: no matter how large a `width`/`height`/`windowWidth`/`windowHeight` you ask html2canvas for, the cloned elements still visually clip to their own on-screen scrolled box, so only whatever already fit in the visible viewport got captured -- exactly the "small box, rest blank" symptom. Confirmed directly against the real html2canvas 1.4.1 source and reproduced/fixed in an isolated headless-browser harness (the previously-shipped width-only fix from v2.15.0 was verified to still fail this same way) before touching production code. Fixed by neutralizing the overflow on the cloned `.chart-panel` and `.gantt-container` via html2canvas's `onclone` callback, pinning them to their true full-content dimensions instead.
- [x] ~~[BUG] Grid-typed or Bulk-Edited Resource names weren't reaching the named-resources registry (backlog #12).~~ -- **fixed in v2.22.1.** The registry only picked up a new name via CSV import's merge step; typing a not-yet-registered name directly into a grid Resource cell, or setting one via Bulk Edit, assigned it to the task fine but never added it to the Resource Manager or that cell's own quick-pick popover. Fixed with `mergeResourceNamesFromValue()`, run from the grid's Resource-column change handler (a direct edit and Bulk Edit's per-row writes both go through it), doing the same additive merge CSV import already did for a whole file, but for one cell.

11. ~~Undo/redo~~ -- **done in v2.23.0.** Whole-snapshot, not a per-cell diff/command log: a cell edit can cascade through dependency scheduling and parent rollup, so reverting just the touched cell would leave every computed field downstream of it stale. Undo/redo instead restores a full prior snapshot of the task data and feeds it back through the existing render+sync pipeline (`renderGrid` + `syncToGantt(true)`), so Outline numbers, computed dates, and parent rollups all come back correct together. Toolbar buttons plus Ctrl+Z/Ctrl+Y (intercepted ahead of jexcel's own document-level keydown handler, so its unreliable per-cell history -- the exact thing this item's own description called out -- is bypassed entirely rather than fought with); history is per-project, in-memory only, capped at 50 steps. Deliberately does **not** cover custom column add/rename/delete, the Resources registry, or collapse/label-filter UI state -- scoped to the task data grid only, which is where the cascade risk this item worried about actually lives. Building it also surfaced and fixed a real correctness gap in Bulk Edit and resource-rename-propagation, both of which fired the grid's per-cell change hook once per row and would otherwise have produced multiple undo steps for one user action.
12. ~~Treat Resources as first class entity. I'd like them to be assigned (named) prior to being typed in the grid. This should allow a pre-selected value for me to use. Discuss how to handle this when its done via CSV Import/Export.~~ -- **done in v2.20.0.** (A per-project "named resources" registry -- add/rename/delete via a new "Resources" toolbar button/modal -- plus a quick-pick ▾ icon on every grid Resource cell, opening a checkbox popover of registered names to toggle on/off for that task. Deliberately did *not* turn the Resource column into a real jexcel `dropdown` (as Depends/Parent already use): that would force every stored value to be one of the dropdown's own source items, which would either break the inline allocation syntax `parseAssignments()` already depends on -- tested behavior like "Alice (50%), Bob" -- or require registering "Alice (50%)" itself as a distinct resource. Instead the registry is a purely additive quick-pick layer; the Resource cell stays the exact same free-text, comma/semicolon field it always was, allocation annotations included. CSV decision (the one this item itself asked to have made): the Resource column's CSV shape is unchanged -- the registry is new per-project metadata alongside `columns`/`collapsed`, not part of the task CSV -- and importing a CSV that mentions a not-yet-registered name merges it into the registry rather than dropping it, so the picker stays complete without retyping every name after an import. Renaming a registered name in the modal also updates every task cell already assigned it (preserving any allocation suffix verbatim), so a rename doesn't silently orphan existing assignments; deleting a name from the registry only affects future quick-pick suggestions and leaves existing task text alone.)

15. **Mobile responsiveness and PWA support** -- the layout (split grid/chart panes, jexcel's own grid interactions, the toolbar) is built and tested for a desktop-width screen only; nothing today targets touch input or a narrow viewport. Highest risk/complexity item on the list: a real mobile-usable Gantt grid likely needs its own responsive layout strategy (e.g. a stacked or single-pane-at-a-time view below some breakpoint, touch-sized tap targets, jexcel's own touch-drag behavior verified), and PWA support on top of that (a web app manifest, an icon set, a service worker for offline caching) touches how the app is served/installed, not just its CSS. Needs real design/UX thought on what "mobile Gantt editing" should even look like before writing code, not just a `@media` pass over the existing desktop layout.
16. ~~CSV export: visually indent Task Name by outline depth to mirror the grid's parent/child indentation.~~ -- **done in v2.21.0.** `exportCSV()` now prefixes each exported Task Name with 4 spaces per level of Parent-chain depth, reusing the exact same depth walk `formatCells` already used for the grid's own indentation -- pulled out into one shared `computeTaskDepth()` helper rather than a second copy. The one open design question this item flagged (whether the indent should be stripped back off on import) is resolved: it is, unconditionally, on every ingestion path (`sanitizeImportedCell`) -- depth is always recomputed fresh from Parent on import, so a leading-space prefix in a raw CSV is never meaningful data to preserve, and stripping it means an export -> re-import -> re-export cycle can't compound into double indentation.

17. **[FEATURE] Toolbar visual review -- reduce clutter, more user-friendly layout.** Self-requested review of the toolbar's current visuals (`index.html`, the `.toolbar`/`.toolbar-group`/`.tbtn` block starting ~line 158). As-is: a single flat row of 5 `toolbar-group`s holding ~26 controls (Start/Today/Workload/Expand All/Collapse All; search + label filter; zoom select/3 inline checkbox toggles/Grid/Split/Chart; Add row/Bulk Edit/Resources/Fit columns/Sync Dependencies/Import/Export CSV/Export PNG/Export PDF; Back up/Versions/Disconnect), every button rendered at identical visual weight (same `.tbtn` icon+label style regardless of how often it's used), with no primary/secondary distinction and no overflow mechanism beyond `flex-wrap: wrap` silently reflowing into extra rows on narrower windows. Recommendation, roughly ordered by how contained the change is:
    - **Group the 4 export formats behind one "Export ▾" menu** (CSV/PNG/PDF export + Import) instead of 4 separate always-visible buttons -- lowest-risk change, pure UI restructuring with zero behavior change to the export functions themselves.
    - **Move the 3 inline checkboxes (Weekends off, Critical path, Label in chart) into a single "View options ▾" menu** alongside Zoom, rather than as separate labeled checkboxes competing for horizontal space with everything else.
    - **Fold rarely-touched actions (Fit columns, Sync Dependencies) into the same overflow/"More ▾" menu** rather than permanent top-level buttons -- both are recovery/utility actions, not everyday ones.
    - **Give the remaining always-visible buttons a visual hierarchy** -- e.g. Add row and Back up as filled/primary, navigation (Start/Today) and view-mode (Grid/Split/Chart) as a lighter segmented-control style, everything else as plain ghost buttons -- instead of every button sharing one `.tbtn` treatment regardless of frequency of use.
    - Net effect: collapse ~26 top-level controls down to roughly 10-12 (nav/search/view-mode/Add row/a couple of menus/Back up/Versions), which should also remove the need for `flex-wrap` to silently spill onto a second row on laptop-width screens.
    **First cut done:** the Export menu grouping shipped -- Import CSV / Export CSV / Export PNG / Export PDF collapsed behind one "Export ▾" toolbar button (`#exportMenuBtn`/`#exportMenuDropdown` in `index.html`), same anchored-popover open/close pattern already used by the label filter dropdown (`toggleLabelFilterDropdown`/its outside-click listener). The four action buttons keep their original `onclick="exportCSV()"` etc. attributes unchanged -- a separate delegated click listener on the dropdown closes the menu after any action fires, rather than editing each handler, so nothing about the export/import functions themselves changed. The other three recommendations (View options ▾ for the 3 inline checkboxes, folding Fit columns/Sync Dependencies into a More ▾ menu, and a visual-hierarchy pass on the remaining always-visible buttons) are **not** done -- left here for a future pass, still lowest-risk-first.
